## 1. What we're building

**Blumea** (blumea.io) is a *Social Content Intelligence* platform for creators (later: social managers, agencies, brands).

- Tagline: **Your content. Our insight. Your growth.**
- Core idea: not just *what* succeeded, but *why*, and *what to do next*.
- Core principle: **Analyze deeply, present simply.** Insight-first, not chart-first.
- Product role: analysis, understanding, comparison and guidance. **Not** generating the creator's content for them.
- Users should never need to "know analytics" to get value.
- **Differentiator vs. the market** (see §12): explicit fact/inference/recommendation separation, shown to the user as a visible trust signal, not just an internal rule.

The user connects their accounts (YouTube, Instagram, TikTok — user's choice), Blumea reads their content and performance, shows what it *understood* about each video, connects that to viewer behavior, gives specific recommendations, and suggests comparisons that can actually teach something.

Full vision document: `docs/Blumea_Product_Vision_Summary_HE.docx` (Hebrew). Keep it in the repo; this file summarizes it and adds platform constraints and business context found later.

## 2. Product structure (locked decisions)

**Navigation (fixed sidebar):** Dashboard, Content, Insights, Connections, Settings.
- *Analyze* is NOT a sidebar item. It's a central action reached from Dashboard or Content.
- *Analyze & Compare* is one workspace. Parameters are chosen in a **modal**, not extra pages.
- *Connections* = connect / disconnect / reconnect accounts. Dashboard is not a connection-management screen.

**Onboarding (4 steps):** Goals → Content Categories → Platforms → Connect Accounts. Then an automatic **First Scan** of up to the last 50 videos — numbers only, no AI — plus a **First Look**: AI analysis of just 3 videos. (See §6. Decided 2026-09-26: analyzing all 50 with AI is too slow and too costly for a user who hasn't paid.)

**Dashboard** = snapshot, not a control room: greeting, key KPIs, period + platform selector, main CTA to Analyze, Blumea Insights (short conclusions), Top Content cards, Trends for you. Dashboard V1 is considered locked unless a functional need appears. (Note: "Trends for you" has no confirmed data source yet — see §7.)

**Analyze flow (locked, per platform — see §6 for the exact per-platform steps):** Analyze → choose platform → choose video from the in-app list → choose analysis path (Lite vs. upload for Deep, or automatic Full for YouTube) → Analyzing (Blumea flower + progress steps) → Analysis result.
Analyzing steps shown: Reading video content · Understanding text & subtitles · Identifying hooks and key moments · Analyzing viewer behavior · Finding useful patterns. Later, tie these to real pipeline statuses.

**Analysis Overview screen (in order):**
1. Video identity + platform, then **raw metrics only** (Views, Likes, Comments, Shares, Saves) — facts, no good/bad judgment.
2. **What Blumea understood — Content Identity** (compact list, not cards; fields are dynamic per content type): Topic, Categories, Format, Subtitles, Textual Hook, Visual Hook, Sound, Trend, subject-specific fields (Game, Map, Dish, Song, Artist, Product…). Each field carries a **confidence badge** (see §12).
3. **Recommendations** next to Content Identity: **KEEP / IMPROVE / TRY NEXT** only.
4. **Viewer Behavior** summary (not a heavy chart): Average watch time, Opening retention, Biggest drop, Strongest moment. Button → *View detailed analytics*.
5. **Recommended Comparisons** (2–3, only if genuinely useful).

**Detailed Analytics** = second layer: retention graph, completion rate, 3-second retention, rewatch rate, engagement rate, timeline.

**Evidence Player:** when the video is shown, it's an interactive player. Recommendations/moments (e.g., Biggest drop) link to exact timestamps. Use the platform's own player/embed where supported. Blumea is **not** a video-hosting service.

## 3. Principles for AI output (important)

- Separate **fact**, **inference**, and **recommendation**. Never blur them.
- Show what was understood *before* recommending.
- Every recommendation answers: **what we identified → what happened → what to do.** It must point at a specific element of the video. Never generic ("Strong hook").
- Be **specific only when confident.** Low confidence → broaden instead of inventing precision (e.g., "First-person shooter gameplay", not "CS2", if evidence is weak). Store a **confidence value per Content Identity field**, and surface it in the UI (§12).
- Hypotheses use cautious wording ("suggesting this section may contribute"). Never assert causality we can't prove.
- Don't declare a Trend without enough evidence.
- Tone: friendly, calm, clean, non-judgmental, points to evidence, explains uncertainty, proposes the next experiment. Small celebratory micro-moments when the user progresses.
- Small samples are noisy (small channels). Surface "not enough data" honestly.

**What the product may say, and when it must stay silent** (claim levels, thresholds, trust tiers per AI field, comparison and pattern rules): see `doc/Insight_Engine_Spec.md` (draft). Rule of thumb: code decides what may be said; language only phrases it.

**Content Identity hierarchies (examples):**
- Gaming: Niche → Game → Topic → Map/mode/mechanic
- Food: Niche → Dish → Recipe type → Trend
- Music: Niche → Content type → Song → Original artist → Style

**Comparison matching principle:** start from the most specific comparison with enough data, widen only if the sample is small. Example: CS2 Mirage smoke tutorials → CS2 smoke tutorials → CS2 tutorials → FPS tutorials → Gaming tutorials. Show fewer options rather than padding.

**Compare dimensions (long-term direction):** Video↔Video, Creator↔Creator, Video↔Creator, Hook↔Hook, Topic↔Topic, Format↔Format, Sound/Trend↔Sound/Trend, recent performance↔baseline, own content↔relevant niche content.

## 5. Platform reality (what the APIs actually allow)  **[VERIFY all]**

General: OAuth gives access **only to what each platform's API exposes**, not free access to an account. "The user granted permission" ≠ "we can read/see the video." Analyzing video content requires pixels/audio (or transcripts derived from them) to reach our system.

### YouTube (start here) — **decided approach: URL-model, no upload**
- YouTube Data API + YouTube Analytics API via Google OAuth. Requires Google's API/scope review.
- Owner analytics include retention data (best source for Viewer Behavior).
- Video **file is not downloadable** via the API. Downloading by other means violates ToS. YouTube also has no manual "download my video" button (unlike IG/TikTok), so there is no manual Deep-upload fallback if the URL-model path fails.
- **Decision:** Full analysis runs via a model that accepts the YouTube URL directly (e.g., Gemini), without any download or upload step. Lite (metadata-only) is the fallback if the URL-model path is unavailable or fails. **Tested 2026-09-26:** works on public YouTube Shorts from the URL alone (15 of 15 calls succeeded, no download or upload) — see "AI validation findings" in §13. Public videos only (not private/unlisted). **[VERIFY]** terms and quotas again before launch.
- Owner's captions are accessible as a secondary/backup text source.
- Check YouTube API Services Developer Policies for storage/refresh rules on stored API data (affects baseline history and "Recent comparisons").

### Instagram
- **Checked live 2026-10-01 against current Meta docs (not yet connected, so not tested with real data):** per-Reel `ig_reels_avg_watch_time` (real average watch time) and `reach`/`likes`/`comments` via Media Insights. Account-level (not per-video) `follower_demographics` and `engaged_audience_demographics` — age, city, country, gender breakdowns — via the User Insights endpoint, needs `instagram_business_manage_insights` (or `instagram_manage_insights` on the Facebook Login variant) and ≥100 followers/engagements. This is the mechanism for "what audience likes this creator overall," not just per video.
- Business or Creator accounts only. Prefer **Instagram API with Instagram Login** (no Facebook Page required); some fields (e.g. `saved_count`, `shares_count`, `reposts_count`) are documented for the Facebook Login variant only.
- `media_url` gives a **temporary** link to the video file for processing (pull, process, discard; never store).
- **Since 2026-07-30, `media_url` is omitted** when the video has copyrighted/licensed audio (including Instagram audio library music), even for the user's own media. Use the `media_audio_type` field (`MUSIC` vs `ORIGINAL_SOUND`) to decide the path up front — this is one of the two cases routed to manual upload (see §6).
- Insights: views, reach, saves, shares, average watch time, and `reels_skip_rate` (closest thing to "opening retention"). No per-second retention curve. Older `video_views`, `plays`, `impressions` are deprecated.
- Minimum-follower thresholds for insights exist (100 per changelog for account insights; a third-party source claims 1,000 for Reels insights) — **check**, it affects small creators.
- Business Discovery API: public data of *other* Business/Creator accounts (e.g., `view_count`). Useful for competitor comparison via metrics only. Unclear whether video files are reachable this way — do not build on it before reading the full docs.
- Meta App Review / business verification required (see §10).

### TikTok
- **Verified live 2026-09-30:** the desktop web share menu (tiktok.com) has no download/save option at all — only Embed, WhatsApp, Copy link, Send to friends, Repost. TikTok's native "Save video" only exists in the mobile app. Product copy for the "open in TikTok to save" helper must send creators to their phone, not assume desktop works.
- Login Kit + Display API: per video → id, create_time, title, video_description, duration, width/height, cover_image_url (**expires after ~6h**, refresh via video/query), share_url, embed_link/embed_html, like count etc. **No video file.** This is why TikTok is always routed to manual upload for Deep analysis (see §6).
- ~~Business/Organic API (Business accounts only): reach, full-video-watched rate, total & average time watched, impression sources, audience countries.~~ **Corrected 2026-10-01, checked directly against TikTok's current, complete scopes list:** no such product exists in the developer platform anymore (if it ever did in this form) — the only scopes available to any third-party app are `user.info.basic/profile/stats`, `video.list/publish/upload`, Research API (vetted academics only), and Portability (user's own data export). **No scope anywhere grants watch-time, audience demographics, or country data** — this isn't gated behind a Business account, it simply isn't offered to third-party apps at all. What a creator sees in TikTok's own app (follower demographics, territories) is TikTok's first-party in-app analytics; it says nothing about what's exposed via API.
- Data Portability API: user-authorized export (posts/profile incl. "video" category) **but only for users in the EEA/UK**, requires application (~3–4 weeks review) plus separate Login Kit approval. Not usable for Israeli users. Unknown whether it returns actual video files.
- Research API: academic/non-profit only. Not for us.
- oEmbed (official): title, creator, thumbnail, embed code from a link. **The embed HTML includes a link to the video's sound** (e.g. "♬ original sound - creator") pointing at the sound's page — per TikTok's docs, the only official way found to read a TikTok sound name, and it also covers other creators' viral sounds. **Tested live 2026-09-26** on two public videos (short `vt.tiktok.com` share links are accepted, no login or key needed): it returned `♬ som original - 1F101` (another creator's original sound) and `♬ original sound - EladFast` (the video author's own), each with a sound-page URL containing the numeric sound ID. The label text is localized ("som original"), so store the sound ID, not the label. Not returned: how many videos use the sound. Check terms and rate limits **[VERIFY]**. The Display API video object (id, create_time, cover_image_url, share_url, video_description, duration, height, width, title, embed_html, embed_link, like/comment/share/view counts, is_aigc) has no audio field.
- Fetching TikTok pages/videos by link is blocked for automated access (robots.txt). Do NOT build scraping.

## 6. Analysis modes and the exact upload flow (locked)

Abstract a **video source** so the analysis pipeline doesn't care where frames/audio came from. Three modes, shown transparently in the UI:

1. **Full (automatic, no upload):** YouTube (via URL-capable model), and Instagram videos with original sound. Frames + audio + transcript + metrics. No user effort.
2. **Lite (automatic, all platforms):** metadata, title/description/hashtags, cover image (vision on the cover), duration, metrics. Gives partial Content Identity immediately. Cover alone can reveal on-screen text hooks.
3. **Deep (optional upload):** TikTok (always, no file API), and Instagram Reels with licensed music (`media_audio_type = MUSIC`). 

**Locked UI flow for TikTok and Instagram-with-music:**
1. User taps **Analyze** and picks a platform.
2. User picks a **video from the in-app list** (pulled via API after the account is connected) — not a free-form URL paste.
3. In the **same screen/step**, the user chooses: **Lite** (instant, automatic) or **upload the file for Deep/Full analysis**. Both options are presented together, not as separate flows or separate screens.
4. If the user uploads, support **multi-file drag-and-drop** and auto-match uploaded files to the selected API video (by duration/cover similarity), so re-selecting per file isn't needed.
5. The UI explains exactly what upload adds (Visual Hook, audio, sound, scene cuts) so the choice is informed, not a blind gate.

**YouTube flow:** no video-selection-then-upload branch — analysis runs automatically via the URL-model path once a video is selected; Lite only triggers as a fallback if that path fails.

**First Scan and First Look (decided 2026-09-26):**
- **First Scan (seconds, no AI):** fetch metadata + metrics for the last ≤50 videos and build the baseline (e.g. median views, engagement). The user goes straight to the Dashboard; nothing blocks on AI.
- **First Look (AI, 3 videos only):** analyze the strongest, the latest and the weakest video, in parallel, and show each result as soon as it is ready (≈ $0.02 and ≈ 10–20 s in total, from the measured ≈ $0.006 and ≈ 6–7 s per Short). More analysis is on demand.
- **Why not all 50:** measured, 50 full analyses ≈ $0.30 and ≈ 5.5 min in sequence. The money matters less than the wait at the most sensitive moment and the abuse risk on free accounts (1,000 sign-ups ≈ $300 vs ≈ $20).
- **Paid plans:** older videos are analyzed in the background, with a notification when ready. Google's Batch mode is listed at 50% off (≈ $0.003 per video; not tested yet **[VERIFY]**).
- **Cost guards:** cache results per video ID + prompt version (a public video isn't analyzed twice for two users); one First Scan per connected platform account; verified email; monthly analysis cap on the free plan (§10).
- **Patterns:** metric-only patterns (e.g. length vs engagement) can be shown right away and must say how many videos they rest on. AI-based patterns (e.g. hook style vs retention) appear as analyzed videos accumulate.

Goal: user does as little as possible. Never require upload as a gate — make it an optional upgrade, offered in the same step as Lite, not after it.

## 7. Comparisons and Trends — honest status

- "Compare with other creators / the market" and "Trending Sound/Hook/Idea" need data we do not have yet. No official trend API for YouTube Shorts or TikTok. Instagram has a new Audio API (Facebook Login variant) that can surface trending audio **[VERIFY]**.
- **"Compare with Others" is officially "Coming Soon"** — gated by community size/opt-in volume per content category, **not** by source platform. Since comparison operates on extracted profiles/embeddings (not raw video), YouTube performs equally or better once analyzed, given its superior native retention data.
- **Do not build a global database of all social content.** Strategy: on-demand analysis, cache results, store only small structured data (profile JSON, embeddings, external IDs, timestamps), TTL-based expiry, and a *user-chosen set of competitors* (roughly 20–50 accounts), not "the whole niche".
- Comparison data sources, in order of realism: (1) the user's own videos and baseline, (2) public metrics of chosen competitors (public APIs only), (3) opt-in anonymized benchmark pool from Blumea users (grows over time; minimum sample-size threshold per category before showing anything, to avoid re-identifying small niches), (4) a licensed data provider later.
- Avoid showing fake-looking trends. Show Trends only when real data supports them; otherwise hide or label the section.

## 8. Data, privacy, legal rules

- Store: metadata, metrics, external video IDs, thumbnails only as needed, Content Identity, analysis results (structured, so patterns/comparisons can be queried later).
- Full videos: **temporary processing only**, never permanent storage by default.
- Keep platform selection in the profile separate from actually connected accounts.
- Encrypt OAuth tokens. Support revoke/disconnect, and **delete or refresh platform data on disconnect** as platform policies require.
- Do **not** scrape platforms, use unofficial downloaders, automate a browser logged in as the user, or store user passwords. These violate platform terms and expose the product.
- Privacy policy and Terms of Service are required by every platform's app review — write them early (see §10). Consider GDPR and Israeli privacy law for EU/Israeli users.
- Never commit secrets. API keys, client secrets and tokens go in environment variables (`.env` is gitignored).
- **Trademark check (done 2026-09-24):** searched the Israel Trademark Office, WIPO Global Brand Database, and USPTO for "Blumea". No conflicts in Nice Class 9 (software), 35 (business/advertising) or 42 (SaaS) in any of the three. All existing "Blumea" marks are in unrelated classes (food, jewelry, cosmetics, textiles) — "Blumea" is a plant genus name, which explains the pattern. One EU registration (Class 41, "entertainment/education") is the closest adjacency and worth a second look later. No existing software/app used the name. `blumea.io` was unregistered at check time. This is a preliminary check, not a professional clearance search — have counsel (see §10 brief) run a formal one before actually filing a trademark application.
- Other users' content: never build a flow that downloads/uploads other creators' videos for comparison — legally risky independent of technical access. Competitor comparison uses public API metadata/embeds only, never their video files.
- Own-content-only + explicit opt-in for the benchmark pool is Blumea's safe-harbor position: consent at upload, technical partial-verification (hash/duration match against the connected account's own API video list), a real takedown/response process if ever notified of misuse.

### Solo-founder cost model — target near-$0 at MVP stage
Goal: cost floor near $0 for the first 0→~100 users, growing only alongside paying users, not ahead of them.

- **Hosting:** free/cheapest tier (Vercel/Railway/Render, or Supabase for DB+Auth+Storage on its free tier).
- **AI analysis:** the free tier (measured: 20 requests/day per model) is for private tests on public videos only. Google may use free-tier content to improve its products, which contradicts §8 for real users, so real users need the paid tier (content not used to improve Google products). Prepaid credits (minimum $5) stop all requests at a $0 balance, which is a hard cost cap; the Google Cloud $300 welcome credit does **not** cover the Gemini API. Measured cost ≈ **$0.006 per Short** at paid pricing (gemini-3.8-flash: $0.75 / $3.75 per 1M input / output tokens through 2026-12-31, doubling on 2027-01-01 per Google's pricing page — re-check before relying on it).
- **Transcription: evaluated 2026-09-27, decision is DEFER — not built into the product for now.** A dedicated ASR pass (OpenAI Whisper `whisper-1`, $0.006/min) was tested to fix Gemini's wording glitches (a dropped letter in a Hebrew quote, inconsistent wording). It didn't: across 4 hand-checked Hebrew clips, Gemini's wording matched the true sentence every time (one shared miss — a name misheard as a common word, by both tools); Whisper matched only 2 of 4, once substituting several words, once dropping a repeated phrase ("אין אין אין") outright — plausibly because ASR models tend to smooth over disfluent/repeated speech. Small sample, but consistent, and it reversed the original assumption.
  - **What's genuinely still true:** Whisper's word-level timing is real and far more precise than Gemini's (~1fps sampling). But nothing currently in `doc/Insight_Engine_Spec.md` needs that precision — its thresholds (e.g. a 2-second payoff-timing gap) already tolerate Gemini's coarser timing.
  - **Why not add it anyway:** a second paid vendor, a second API key, and a third point of failure, for a benefit with no current consumer.
  - **When to revisit:** a V2 feature that names the *exact word* a retention drop lines up with (not just "around this timestamp") would be a genuine, on-brand use of word-level timing ("point at a specific element", not a generic claim) — worth reopening then, together with a fix for Whisper's word-omission (aligning its timestamps under Gemini's trusted wording, not trusting Whisper's own text).
  - **Scope this would have had, if adopted:** never YouTube (the API exposes no video file, and downloading one by other means violates YouTube's ToS even for our own server — use the owner's free, official, already time-coded captions instead); Instagram original-sound (Full mode) would reuse the file the server already pulls via `media_url` for Gemini; Instagram-with-music/TikTok only if the creator already chose the optional Deep upload (§6) — never a separate ask. Keep this scoping if the feature above ever revives it.
- **Craft/technical signals (new, 2026-09-27):** editing pace, "dead" pauses after a cut, audio loudness, brightness, aspect ratio — measured with ffmpeg, **$0 marginal cost**, no hallucination risk (it's arithmetic on the file, not an AI opinion). Needs a runtime that can run a native binary with enough execution time; check this against the hosting choice below **[VERIFY]** (a plain Vercel serverless function may not fit; Railway/Render more likely do). See `doc/Insight_Engine_Spec.md` §3.4 for what's validated so far and what a whole-frame motion check can't yet tell apart (e.g. background motion vs. an on-screen text overlay changing).
- **Measured cost per video (2026-09-27):** Gemini + ffmpeg, the two tools actually in the pipeline, ≈ **$0.005–$0.007** per video, doubling by 2027-01-01. A 50–60 video/month scan lands **under $0.50/month per active user**. (Whisper is evaluated but deferred, see above — if a future feature brings it back, add ≈ $0.003–$0.006 on the subset of videos it would touch.) Either way, well inside the pricing math below.
- **Video storage:** effectively $0 if files are never retained (see §8) — a free-tier bucket is enough for transient processing.
- **Domain + policy pages:** `.io` domains actually run ~$35–58/year first year, often $46–100+/year on renewal (checked 2026-09-24) — not the ~$10–15 first assumed. Cloudflare or Porkbun quoted as better long-term value than GoDaddy (no aggressive renewal markup/upsells). Policy pages hosted for free alongside the app.
- **Cost grows later with:** paid AI tier past free quota, paid hosting tier past free limits, optional CASA assessment cost at scale, one-time trademark search, and legal counsel for ToS/Privacy/takedown drafting (the one item explicitly kept outside the "do it all myself" scope).

### Pricing (revised 2026-09-27, still revisit once real usage-per-user data exists)
- **Free:** capped analyses/month (e.g. 5), Lite only, no Deep upload, no Compare.
- **Creator: ~$10–15/month** (lowered from the earlier $15–25 draft — the margin supports it; see the margin math below). High/unlimited-feeling analysis cap, background analysis of older videos, Deep upload, Compare-with-self, early access to Compare-with-Others when it ships.
- **Pro/Social Manager:** ~$40–70/month — multiple accounts/profiles, reporting.
- **Margin at $10–15/month** (all-tools cost above + Stripe's 2.9% + $0.30, checked 2026-09-27): net **≈ 76–92%** depending on usage and the 2027 price change. AI/tooling cost is *not* the constraint on price at this level — fixed hosting cost and customer acquisition matter more. Comparable tools, checked 2026-09-27: TubeBuddy Pro $4.50/mo, VidIQ Boost $19/mo, Metricool $20/mo, Virlo $49/mo — $10–15 undercuts three of four while keeping strong margin.
- **Graceful degradation, not partial-looking failure:** with three independent tools (Gemini, Whisper, ffmpeg), any one can fail without breaking the others — cache each tool's result per video so a retry doesn't re-pay for the parts that already succeeded. If a non-core tool fails, drop that section entirely (never show an empty placeholder). If Gemini itself fails, retry automatically rather than showing a part-empty analysis — it's the backbone most of Content Identity depends on.

- All three overlap with Blumea on cross-platform OAuth connections and hook/retention analysis; Metricool and Virlo also do creator-vs-creator benchmarking already.
- None of them visibly separate fact / inference / recommendation with per-field confidence — this remains Blumea's clearest point of difference (formalized as the **Trust Layer**, §12).
- Virlo's growth curve (62K users in 10 months, bootstrapped, no paid ads) is the relevant proof point for a solo/small operator: focused video-intelligence products can grow fast without a large team or budget, if the product is sharp and narrow.
- Suggested wedge: a Hebrew-speaking creator market entry before competing head-on internationally — none of the researched competitors appear to target it specifically.

## 12. Differentiator: the Trust Layer (new — not yet designed in detail)

A visible, product-level expression of §3's fact/inference/recommendation separation, positioned as a user-facing feature and marketing point ("the tool that tells you when it isn't sure"), not just an internal AI-prompting rule.

- Every Content Identity field and every recommendation carries a small, quiet **confidence indicator** (not a banner): e.g. a colored dot or short label distinguishing **Fact** (from platform data) / **AI inference** (high confidence) / **Unverified hypothesis** (low confidence, worded cautiously per §3).
- Never louder than the insight itself — see §4 design constraints.
- **Do not use the model's own confidence.** In tests (2026-09-26) it rated almost every field "high" and flipped observed/inferred labels between runs of the same video. Derive them instead: kind (fact vs inference) from the field type, in code; confidence from agreement across repeated runs, capped (inferred ≤ medium; audio details, sound and trend recognition ≤ low). Agreement is necessary but not sufficient — the model consistently heard a guitar as a piano — so cross-check against platform data (captions, `media_audio_type`) where available.
- To be designed: exact visual treatment, copy for each confidence level, and where it appears (Content Identity list, recommendations, comparisons).
- This is a candidate headline differentiator against Metricool/Virlo/ViralDeck (§11) — worth prioritizing in V1 if feasible, since it's cheap to implement (mostly a UI + copy layer over data we already produce) and hard for competitors to copy quickly without rearchitecting their AI output.

### Rules research: what evidence exists, and two YouTube metrics we weren't using (2026-10-03)
- **Web evidence for "what works" is weak.** Searches (YouTube Shorts retention, captions, TikTok hooks) returned almost only SEO/vendor blogs repeating unverifiable numbers ("a study of 3.3 billion Shorts", "captions +80% completion", "70% retention past 3 s"). Genuinely first-party and usable: YouTube Studio's own *Viewed vs swiped away* metric exists (so the opening matters on Shorts), and TikTok for Business advises stating the content proposition in the first 3 seconds (written for ads). Neither says what works *for this creator*. Policy: general evidence may justify an entry in the §5.2 experiment library ("worth testing", never "helps", principle 9) and should be recorded with its source and grade; a *direction* claim stays reserved for the creator's own history (§7).
- **Found in Google's metrics reference (re-verified by live query on 2 real videos):** `engagedViews` (views past the first frame) — 152 of 512 views (30%) and 262 of 1,163 (23%); and `relativeRetentionPerformance` — retention vs. *all YouTube videos of similar length*, only valid *with* the `elapsedVideoTimeRatio` dimension (the plain query returns 400). The 60 s video scores ≈ 0.40 at the start and ≈ 0.15 by 10% in; the 17 s video ≈ 0.59 → 0.54. A platform-supplied baseline that works from video one, no 10-video minimum. **Checked against the owner's own YouTube Studio the same day (60 s video):** `engagedViews` = 152 matches Studio's "Engaged views" exactly, and average view duration 0:19 (32.4%) matches exactly. Studio's "Stayed to watch" is **27.4%** (swiped away 72.6%), while our `engagedViews ÷ views` gives 29.7% — close but not equal: Studio's denominator is ≈ 555 (152 ÷ 0.274, presumably Shorts-feed impressions, which the API doesn't expose), not the 512 views. So the exact "swiped away" percentage is **not obtainable via the API**; `engagedViews ÷ views` is an approximation (~2 points high here) and must be labelled as one. **Still not confirmed:** the `relativeRetentionPerformance` scale's meaning (is 0.5 "typical"?) — Studio's retention screen ("Intro / Top moment / Spike / Dip" key moments) is where to compare it. The temporary `youtube-insights-test` route was extended to run these queries; still to delete.

### AI validation findings (2026-09-26)
Setup: gemini-3.8-flash, YouTube URL only, 5 public Shorts, 3 runs each, prompt v3; script kept outside the repo. Partly checked by hand on 4 of the 5 videos.
- **Reliable:** exact on-screen text (correct on all four hand-checked videos, e.g. the hook quote matched the subtitle exactly — but when several text elements are on screen, a run may return only some of them, so return a list of texts rather than one quote), whether subtitles are present, speech vs music, speech language, categories and format from fixed lists, and key-moment timestamps (within about 1–4 s across runs when the same moment is reported).
- **Unreliable:** free-text descriptions vary in wording (word-overlap agreement is a poor measure of that — a semantic judge is needed); quiet background music; song identification (in one run the model confidently named a song that was wrong — the real sound, checked by hand on YouTube, was a different track — while the looser v2 prompt correctly named a meme sound that the stricter v3 prompt suppressed: a precision/recall trade-off, so any song the AI names must be shown as an unverified hypothesis; YouTube itself shows the sound's real name, but the official YouTube and Instagram APIs do not expose it (TikTok's oEmbed embed HTML does, see §5) — checked 2026-09-26: YouTube Data API v3 has no music/sound field; the Instagram Graph API only returns `media_audio_type` (MUSIC or ORIGINAL_SOUND), no title or artist; services that do return sound names use unofficial endpoints, which §8 forbids. So: sound *type* is a fact (from metadata where it exists), a named song is only ever an unverified hypothesis); quotes of spoken words (small transcription glitches); which moments get reported.
- **Prompt lessons:** define "speech" as spoken words only (singing is separate; music videos need a sung-lyrics hook field, and a language answered as a name, not a code); separating on-screen text from speech works; returning on-screen text as a list (label, card, caption) fixed the "only some of the text" problem (football video: 3/3 runs complete). Telling the model not to name instruments did **not** fully work — "piano" came back in 1 of 3 runs — so the prompt now bans instrument names entirely and instrument claims are never trusted.
- **Round 2 (2026-09-26, prompt v4, 5 YouTube Shorts × 3 runs + hand-checked truth file):** 52 of 57 checks passed; 3 of the 5 misses were a checker artifact (language answered as "he"), 2 were real: one Hebrew subtitle quoted without a letter in 1 of 3 runs, and the "piano" claim. Hebrew quotes can lose a letter in about 1 of 3 runs, so a quote should be the majority wording across runs or come from platform captions. The language of sung lyrics is unreliable (one song was heard as French, Spanish and Italian in different runs). A song-name guess appeared once for a meme sound (close to the real name) and stayed empty where the earlier run had invented a wrong one. The AI judge for free-text agreement is lenient (it called "with piano" and "without piano" the same), so caps on audio and name fields stay.
- **Lite (cover + caption only), measured:** works for text on the cover, a description of the cover, the caption's language, rough topic and categories. It cannot hear or watch: a Hebrew song video was classified as comedy/lifestyle, so Lite misleads for music creators. A YouTube thumbnail is not the first frame (it showed a different scene than the hook), and YouTube's oEmbed only gives the title, while TikTok's gives the full caption with hashtags. Cost ≈ $0.004 per call vs ≈ $0.0064 for a full analysis: only ~40% cheaper, because output/thinking tokens dominate, so Lite's value is that it needs no video, not that it is cheap. Whether a lower thinking level cuts cost is untested.
- **Platform sound (TikTok oEmbed):** worked on 3 of 3 links, including a Hebrew-localized label ("צליל מקורי - אליסף"), so the label language varies and the sound ID is what to store. For the downloaded file of one of those videos the AI said "original speech" and the oEmbed said the video's own original sound — consistent.
- **Cost and speed:** ≈ $0.0064 per full analysis of a Short (plus ≈ $0.002 per video for the AI judge in tests only); 18 calls with 3 at a time took 48.7 s, so a First Look of 3 videos in parallel takes ≈ 9–10 s. A local video file works (a 1.4 MB TikTok download analyzed 3/3); files over ~18 MB go through Google's Files API and must be deleted right after use (§8).
- **Thinking level "low" (tested 2026-09-26, 7 videos × 3 runs):** ≈ 30% cheaper (≈ $0.0048 vs ≈ $0.0070 per call, including the test-only judge) and ≈ 30% faster (≈ 5.7 s vs ≈ 8 s per call); all 21 calls returned valid JSON (at the default level 1 of 24 did not), and answers were at least as consistent (moments, comment-card text, and the meme-sound name guess appeared in 3 of 3 runs). Small sample: re-check on the golden set. Either way production needs schema validation with one retry on invalid JSON.
- **Instagram and TikTok files:** a 41.8 MB Instagram Reel worked through Google's Files API (upload, analyze, delete right after); a 1.4 MB TikTok download worked inline. Text that is part of the scene (a shop sign) was returned as on-screen text, so on-screen texts need a "scene" role. Sung lyrics in English varied a lot between runs — not a field to build advice on.
- **Not tested yet:** Google's Batch mode, longer videos, a second-model cross-check, and a golden set of ~30–50 hand-labeled videos for regression checks (a one-time development test set, not what a user goes through).
